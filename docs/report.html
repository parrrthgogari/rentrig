Technical Report
1. RSC vs. Client Component Render Trees

RentRig is architected using the Next.js App Router paradigm with React Server Components (RSC) for data-driven, non-interactive catalog presentation, and Client Components for browser-side stateful interactions.

Server-rendered components include the equipment discovery catalog (app/(public)/equipment/page.tsx), detailed hardware specifications (app/(public)/equipment/[slug]/page.tsx), and administrative oversight dashboards. Client Components handle the interactive rental reservation cart, multi-criteria facet filtering, date pickers, theme controls, and persistent storage synchronization.

This server-first pattern keeps client boundaries strictly confined to interactive leaves of the component tree, drastically cutting unnecessary JavaScript shipped over the wire and eliminating layout waterfalls.

Hydration Optimization

RentRig optimizes client hydration through the following architectural principles:

  • Focused Client Boundaries: Declaring 'use client' exclusively on leaf interactive components (forms, filters, theme toggle).
  • Serializable Prop Boundary: Passing only clean JSON-serializable primitives (numbers, strings, dates) across Server-to-Client boundaries.
  • Hydration Mismatch Prevention: Applying suppressHydrationWarning on the document root and synchronizing dark/light modes with CSS variables via next-themes.
  • Decoupled State Slices: Storing temporary rental configurations inside Zustand rather than global React contexts, preventing layout re-renders.
  • Asynchronous Streaming: Wrapping database-dependent UI segments in React <Suspense> fallback skeletons.
2. Server State vs. Zustand Client State

Server state remains authoritative for equipment availability, confirmed bookings, and pricing. Zustand manages the reservation cart because users require immediate feedback when adjusting dates or adding items across different product pages.

During checkout, the server route handler (POST /api/reservations) validates all submitted equipment IDs, dates, and calculated totals against database records before creating the reservation. Therefore, client state dramatically improves interactivity without compromising data integrity.

System Architecture
1. System Overview

RentRig is a full-stack high-end hardware and compute rental platform built with Next.js 16, Prisma ORM, PostgreSQL, Better Auth, React Email, and Resend. The application supports hardware browsing, multi-role session control, transactional reservations, and automated email delivery lifecycle logging.

The relational data tier uses PostgreSQL managed by Prisma ORM for type-safe migrations and transactions. Realistic seed data is programmatically populated using Faker.js via prisma/seed.ts.

Main Entities
  • User: Stores credentials, email verification status, and assigned RBAC roles (ADMIN, MEMBER, GUEST).
  • Session / Account: Persists session cookies, authentication tokens, and expiry dates via Better Auth.
  • Equipment: Holds hardware specs, daily rental prices, availability flags, and categorized JSON specs.
  • Reservation: Connects users to rented hardware with date ranges, calculated pricing, and status enum (PENDING, CONFIRMED, ACTIVE, COMPLETED, CANCELLED).
  • AuditLog: Tracks operational events (action, entity, client IP, user agent) for administrative auditing.
  • EmailEvent: Captures lifecycle delivery, bounce, and open records sent by the Resend webhook.

The application supports three roles:

  • Guest: Unauthenticated user who can browse hardware, inspect specs, and manage a client-side cart.
